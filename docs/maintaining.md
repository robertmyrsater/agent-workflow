# Maintain a living workflow

Keep this repository general and each adopting project specific. A useful
improvement is a clear rule or reusable template that prevents a demonstrated
coordination mistake; it is not a copy of a project's conversation history.

## Where a change belongs

| Change | Home |
| --- | --- |
| General ownership, handoff, verification or setup lesson | This repository, reviewed PR plus changelog |
| Product requirements, named people/chats, service choices and runtime commands | Project overlay and project documentation |
| Current tasks, approvals, deployments and test results | Project status records and dated evidence |
| Credentials, private messages, customer records and raw sessions | Approved restricted systems; never this repository |
| Tool installation or feedback behavior | Tool's maintained instructions, with project/work approval |

## Propose and review a general change

1. Explain the demonstrated problem and the smallest general correction. Use
   sanitized examples; do not copy private incident logs or account identifiers.
2. Update the affected guide/templates together. Preserve human authorization,
   original-outcome verification and local policy boundaries. Identify changes
   that would alter project behavior.
3. Have an independent reviewer check practical usability, internal links,
   template consistency, privacy and authorization implications. Verify the
   exact proposed revision; a prior review does not cover subsequent edits.
4. Add a concise entry under Unreleased in the [changelog](../CHANGELOG.md),
   including adoption impact. Publish or merge only within the actual authorized
   scope. This repository's workflow does not grant standing release authority.

## Adopt an update deliberately

A project stays on its recorded reviewed commit until its owner chooses another.
Compare the old and proposed shared revisions, read current local overrides and
record applicable changes and conflicts. Update the overlay's exact SHA,
reviewer/date and adoption note through a reviewed project change. Keep the old
revision and decision in that project's history. Never make a rolling `main`
reference substitute for this review.

Shared updates do not automatically install tools, change global or project
instructions, enable feedback, schedule work, alter access, or broaden approvals.
Existing explicit task authorization remains valid only for its actual scope.
Do not silently reinterpret it because the guide changed. When a proposed rule
conflicts with project policy or employer controls, resolve that conflict before
adoption rather than selecting the more permissive rule.

Review this guide when a real failure or changed tool capability warrants it;
no recurring task or monitor is created by this document. Check official links
when relying on their current behavior. Keep dated evidence honest, correct
current status explicitly and remove duplication rather than growing a policy
archive inside the guide.
